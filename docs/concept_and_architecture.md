# Nest —— 概念与架构设计

这份文档讲 Nest 是什么、由哪些部分组成、边界画在哪里，以及每一条边界为什么在那儿。
它描述的是系统怎么构建的，不是系统当下什么样。

Nest 建立在 [AttaCore](https://github.com/openatta/AttaCore) 之上。引擎相关的概念
（轮次循环、扩展点、场景、权限、压缩）以 Core 自己的文档为准，这里只在需要说明边界时
引用。

---

## 1. 定位

**Nest 是把 AttaCore 装配成产品的那一层。**

引擎负责"跑一个 agent 会话"——装配提示词、调模型、执行工具、管理上下文与历史。
Nest 负责把这台引擎变成一个人能装上、打开、每天用、并且能按自己的需要改造的东西：
会话的持有与追赶、界面、插件、身份与授权、部署形态。

这条分工是硬的，两个方向都是：

- **Nest 不含任何引擎逻辑。** 会话怎么跑、工具怎么派发、上下文什么时候压缩，一律是
  AttaCore 的事。缺的能力去给 Core 提，不在这边补一个平行实现——一个平行实现意味着
  同一件事有两处真相，而它们会分叉。
- **Core 不知道有界面这回事。** 客户端面的协议、贡献点、身份，全部止步于 Nest。

### 1.1 它不是什么

| 不是 | 因为 |
|---|---|
| 一个 agent 框架 | 框架是 AttaCore。Nest 是它的宿主 |
| 一个多租户服务 | 一个进程服务一个用户（多个会话、多台设备）。多租户是另一个系统，不是这个系统的配置项 |
| 一个"什么都能换"的内核 | 骨架不可插拔，见 §2.1 |

### 1.2 三个目标，按优先级

1. **可定制。** 不 fork 就能做出一个形态不同的产品。这是首要目标，其余两条服务于它。
2. **可在边缘部署。** 一个后端二进制，无运行时依赖，冷启动以毫秒计，空载内存以十兆计。
3. **安全边界清楚。** 每一处约束要么是强制的，要么被明说成不是强制的。没有第三种。

## 2. 设计原则

### 2.1 骨架不可插拔

Nest 的内核是四件事：**装配、中枢、传输、授权**。它们不是扩展点，没有替换入口。

理由和引擎把轮次循环的步骤顺序写死是同一个：**顺序与所有权本身就是定义**。一个能被
插件换掉的会话中枢等于没有中枢——追赶不变量一旦可以被第三方重写，"打开一个跑到一半的
会话会看到什么"就不再有答案，而这是产品最基本的动作。

骨架之上的每一个判断都可插拔。分界线画在"这件事的形状"和"这件事怎么做"之间。

**注意"不可插拔"约束的是语义，不是实现形式。** 传输就是个例子：它承载什么、保证什么
是写死的，用几条连接承载不是（§3.3）。

### 2.2 一个系统只有一种插件体系，而它是 AttaCore 的

**插件装到 AttaCore，不装到 Nest。** 包格式、取包、校验、缓存、manifest、能力声明、
安装期披露、沙箱、载体、生命周期——整件事都在引擎那边。

Nest 没有、也不会有自己的插件体系。这不是把工作推出去，是同一条原则的直接后果：一件事有
两处真相，它们就会分叉；而分叉之后往往只有一处是真正拦得住的，另一处是装饰。

一个包里可以有 Nest 关心的一段（界面贡献），但那不构成第二个体系——**一个包、一份
manifest、一次安装、一次披露**。Nest 只是多读一段引擎不关心的配置，然后把一个目录发出去。

#### 2.2.1 Nest 不执行包里的任何东西

一个包可以带 Nest 关心的东西——界面模块——但那是**浏览器**加载的静态资源，不是 Nest 跑的
代码。这一侧读一段配置、发一个目录，仅此而已。

曾经有过一个例外：`[[host]]` 段里的**投影**，一个折叠会话事件流的纯函数，由 Nest 执行。
它没有能力可谈，所以并没有引入第二个"扩展能做什么"的答案——但它让这条规则必须写成
"Nest 执行包里的代码，但只执行那种什么都做不了的"，而**一条带例外的规则是会被人加宽的**。

所以它被撤掉了。现在这条规则不需要例外，也就不需要谁去记住例外的边界在哪：

> **Nest 不执行包里的任何东西。**

由 `crates/app/tests/layering.rs` 盯着：manifest 读取结构体只许有 `ui` 一个字段，整个
crate 树里不许出现任何解释器。

#### 2.2.2 这一节反复过两次，原因写在这里

第一版把宿主侧和界面侧的贡献都算作 Nest 的插件模型；第二版全部撤掉，理由是插件体系是
Core 的；这一版回到"包是 Core 的，Nest 读其中两段"。

中间那次撤销基于一个当时以为成立的前提：**Core 的插件体系在跑。** 后来发现出厂构建里它是
关着的——脚本载体与 WASM 载体互斥，而我们发脚本构建，于是 `plugin.*` 一律
`PLUGINS_DISABLED`，一个包都装不了。正确的修法在 Core（让包方案与载体解耦，见 §9），
不是在 Nest 另起一套。

写下来是因为 §2.5：一份没人检查的承诺会变成谎话，而一份反复改过又没说为什么的设计，
读的人无从判断哪一版是当前的。

### 2.3 信任按出身定，不按声明定

一个来自外面的扩展要撒谎，撒的正是"我需要什么"这种声明。所以级别由它**从哪儿来**
决定：运维本人写在项目里的东西、装上的插件、远端连上来的设备，三者天然不同级。
声明的作用是在已定的级别内**进一步收窄**，不是用来晋级的。

### 2.4 失败的扩展只让它自己那份贡献消失

抛异常、超时、配额耗尽、答出一个用不了的形状——这个点保持原样，别的什么都不受影响。
每个适配器先把改动完整算出来再施加，所以不存在"施加了一半"的状态。

而且**"它什么也没做"是可查询的**：哪个点、哪一轮、结局是被采纳、无可采纳、没答上来
还是被拒绝，都记下来并可以问。否则"我的插件为什么不工作"只能靠猜。

### 2.5 每一条承诺都可检查

贡献点目录由代码生成；层与层之间的依赖方向由测试断言而不是由文档描述；性能预算进 CI 门禁；
内建界面走的就是公开的那批贡献点，而且有测试盯着"外壳真的去问了"。**一份没人检查的承诺，
下一次改动就变成谎话。**

## 3. 内核

```
   ┌──────────────────────────────────────────────────────┐
   │  客户端（界面是独立产物，可分离部署，见 §5）             │
   └──────────────────────┬───────────────────────────────┘
                          │  传输契约（拓扑可选，见 §3.3）
                          ▼
  ┌────────────────────────────────────────────────────────┐
  │  nest（一个二进制，一个进程，一个用户）                    │
  │                                                        │
  │   传输 ── 通道语义、TLS、静态面（可选）                    │
  │   授权 ── 这个进程唯一的准入点：设备、方法、插件能力         │
  │   中枢 ── 会话的持有者：订阅、缓冲、turn 所有权、队列       │
  │   装配 ── 建起引擎：场景、设置层、模型路由、会话池          │
  └───────────────────────────┬────────────────────────────┘
                              │  进程内调用
                              ▼
                    AttaCore 引擎（作为库链接）
```

四个部分之间的依赖是单向的，每一层不认识它上面那层的概念：

| 部分 | 不许知道 |
|---|---|
| 传输 | 会话是什么 |
| 授权 | 帧长什么样、走的哪条通道 |
| 中枢 | HTTP、TLS、连接、拓扑 |
| 装配 | 客户端面协议 |

### 3.1 装配

把引擎建起来：场景集合、设置的层次解析、模型与任务路由、会话池、技能与 MCP 的接入。

装配是**声明式的**：一份配置说清要哪些场景、哪些 provider、哪套界面、哪种传输拓扑，装配
照着做，之后这一轮装配就定了。运行期没有东西能改写它——能改写它的东西等于在决定这个进程
是什么。

扩展不在这里声明：脚本配在引擎自己的设置层里，插件装进引擎自己的插件目录。多一处声明就是
多一处真相。

引擎的根**显式传进去**，不改本进程的环境变量：那样一个进程就不可能服务两个根，状态
也不会藏在调用者看不见的地方。

### 3.2 中枢

中枢是会话的持有者。它的存在理由是一条不变量：

> **中枢永远比任何客户端先订阅。**

会话第一次被打开时中枢立刻订阅并开始缓冲，此后任何客户端的追赶**只在中枢的缓冲区里
进行**。由此得到的四件事，每一件单独看都不足以撑起一层，合起来就是：

1. **刷新页面不丢内容。** 一轮跑到一半刷新，前半段既在缓冲里，也不依赖引擎补发。
2. **turn 不挂在连接上。** `run_turn` 由中枢发起，关掉标签页、切换设备、断网重连都不
   影响这一轮，最终结果广播给所有观看者。
3. **多设备一致。** 同一个会话可以被几个客户端同时看，任何一个都能回答权限提问，先答者
   生效。
4. **排队是产品行为，不是错误。** 引擎对同一会话同时刻只允许一个 turn；这条约束不该
   原样漏给用户。有 turn 在跑时新消息进中枢的队列，上一轮结束后自动发出，队列可撤销，
   整值快照推给所有客户端。

中枢的状态与语义**不可替换**（§2.1）。

**推送一律整值。** 队列、会话列表、引擎健康这类状态推的是完整快照，客户端不做增量合并
——增量合并的错误只在特定顺序下出现，而那个顺序在测试里不容易造出来。

### 3.3 传输

传输是**一组通道语义**，不是一种连接拓扑。**语义写死，拓扑可选。**

这样定的理由很具体：不同的部署对连接的诉求不一样。边缘弱网下少开一条连接是省下的重连
与心跳；放在反向代理后面时，让请求走普通 HTTP 能直接吃到现成的中间件、缓存与限流；
一个只想看进度的只读客户端不该被迫开一条能发请求的双向连接。**这些差异不该逼着中枢
换一套语义。**

#### 3.3.1 五种通道语义

| 语义 | 干什么 | 谁发起 |
|---|---|---|
| **unary** | 一次请求一次应答的方法调用 | 客户端 |
| **会话事件流** | 某个会话的事件：流式正文、工具行、权限提问、压缩 | 服务端 |
| **宿主事件流** | 与具体会话无关的：会话列表、队列、引擎健康、插件状态 | 服务端 |
| **带外应答** | 对服务端发起的提问的回答（权限、澄清） | 客户端 |
| **大负载旁路** | 附件上传、导出下载 | 双向 |

**会话事件与宿主事件从语义上就是两个订阅面**，即使它们最终走同一条连接。一个只看侧栏
的客户端不该为了知道"哪个会话在跑"而接收所有会话的正文流量。

**带外应答之所以单列**，是因为它在只下行的事件流拓扑里没有回程可用。把它当成一个独立
语义，各拓扑就都能诚实地实现它，而不是给某一种拓扑打补丁。

#### 3.3.2 三种参考拓扑

| 拓扑 | 映射 | 适合 |
|---|---|---|
| **单双向流** | 一条双向连接承载全部五种语义（大负载仍走旁路） | 单机、边缘弱网；连接最少，顺序最简单，应答天然有回程 |
| **分离流** | unary 与带外应答走 HTTP；会话事件与宿主事件各一条只下行流 | 反向代理后面、多客户端、只读客户端；请求能用普通 HTTP 设施，两个订阅面可独立断开重连 |
| **纯请求** | 只有 unary 与旁路，事件靠长轮询或服务端推送流补上 | 脚本客户端、受限网络、不需要实时性的自动化 |

三种拓扑的**方法名、参数、错误码、事件形状完全一致**。切换拓扑不是切换协议。

拓扑由服务端配置决定支持哪几种，客户端在握手时选一种；**不匹配就拒绝并说清原因**，
不做静默降级。

#### 3.3.3 跨拓扑的不变量

拓扑可选，但下面这些在任何拓扑下都成立。它们是传输真正写死的部分：

1. **`seq` 是唯一的追赶锚。** 每条会话事件带 `(session_id, seq, turn_id)`，`seq` 由
   **中枢**分配。它不是连接的属性，所以事件走哪条通道、断过几次、跨没跨连接，追赶的
   算法都一样：报出已见的 `seq`，中枢从缓冲区接上。
2. **一次握手，一次协商。** 协议版本、贡献点 API 版本、拓扑选择、能力位，在握手里一次
   谈完。多条通道的拓扑里，后开的通道**携带握手换来的凭据**，不各自再谈一遍——协商谈
   两遍就会有谈出两个结果的那一天。
3. **权限提问的语义与通道无关。** 广播给该会话所有观看者，任一客户端可答，先答者生效，
   第二个回答是静默成功。带外应答走 HTTP 还是走回程，不改变这一条。
4. **大负载永远走旁路。** 附件与导出不挤事件通道，一次性凭据换 URL，落盘后以路径引用。
   这条不因拓扑而变，因为它防的是"一张图片顶满帧上限"这类问题。
5. **中枢与授权不感知拓扑。** 中枢面对的是"一个可以收帧的下游"，授权面对的是"一个已
   认证的主体和一个方法名"。加一种拓扑不会改动这两层——**如果改动了，说明语义被拓扑
   污染了，那是要修的**。

#### 3.3.4 只提供 RPC 的形态

传输可以不提供任何静态资源（`--headless`）。界面在别处，或者根本没有界面（§5.1、§7.1）。

### 3.4 授权

**这个进程只有一个准入点。** 加一个方法，默认是拒绝。

主体只有两类：**内核**（这个二进制自己）和**设备**（配对过的客户端，见 §6.3）。装上的
扩展**不是**这里的主体——它跑在引擎里，受引擎的能力门控约束，够不到这个进程的方法面。
在这一层再放一个"插件"主体，就是第二处决定扩展能做什么的地方（§4.1）。

单用户系统里"这个人能不能做"的答案几乎总是"能"，所以这一层真正在守的是另外两件事：
**引擎那些等价于接管进程的方法一个都不出去**，以及**加一个方法默认是拒绝**。

授权发生在**方法这一层**，不在连接那一层——多通道拓扑里同一个主体可能有好几条连接，
把授权挂在连接上会得到几份可能不一致的答案。

引擎对能到达它的调用方是完全信任的，在这个进程里那就是中枢。**所以引擎那些会改变
凭据、装载子进程、改写模型端点的方法，永远不出现在任何设备或插件的可用集里**——不是
"未实现"，是明确拒绝，并且错误里写清原因。

## 4. 扩展模型

### 4.1 一个包，装到引擎里

一个插件是一个 AttaCore 插件，装的地方也是 AttaCore。包格式（zip）、取包、checksum
校验、解包、版本化缓存、manifest、能力声明、安装期披露、沙箱、载体、生命周期，**全部在
引擎那边**，以 Core 自己的文档为准（`extending_wasm.md` / `extending_quickjs.md` /
`extension_points.md`）。

Nest 不定义包格式、不校验、不解包、不判定能力。它做两件事：

1. **把文件送过去**（§4.2）——引擎自己去取 URL，没有上传通道，而包在使用者笔记本上、
   引擎在另一台机器上时就没有路可走。这一步是宿主的。
2. **读包里引擎不关心的两段**——`[[ui]]` 与 `[[host]]`（§4.6）。读，不是另立一套：
   一个包、一份 manifest、一次安装、一次披露。

### 4.2 Nest 只补引擎有意不做的那一步：收文件

`plugin.install` 自己去取包：

```jsonc
{ "name": "…", "version": "1.0.0",
  "download_url": "file:///abs/path/plugin.zip",   // 或 https://…
  "checksum": "<sha256 hex>",                      // http(s) 必填，file:// 可省
  "scope": "global" }
```

**没有上传通道**，这是引擎的选择。它在包已经躺在跑引擎那台机器上时完全够用；而当包在
使用者的笔记本上、引擎在另一台机器上时，就没有路可走。那一步是宿主的活：

```
   客户端 ── POST /upload ─────────────►  nest              大负载旁路（§3.3）
   客户端 ── nest.plugins.install ────►  nest
                                        nest ── plugin.install
                                                {download_url:"file:///…"} ──► 引擎
```

`nest.plugins.upload` 换一个一次性 URL，`nest.plugins.install` 把落盘路径交给引擎。
其余一律转手：列举、启停、卸载都是直通。

### 4.3 披露在装完之后，因为引擎是那个顺序

引擎装完才回 `disclosure`——这个包会往模型上下文里塞的文本。这与"看过再决定"的顺序是反的。

**采用引擎的顺序。** 界面上就是：装好了，这是它会放到模型面前的东西，留还是删。想在装之前
看，就得在这一侧读包，而那正是这一节存在的目的所要避免的事。

这条约束的性质没有变：**沙箱管得住插件执行什么，管不住它说什么**，所以模型可见文本必须被
人看见。变的只是它在哪一步被看见，以及由谁呈现。

### 4.4 装插件是这个人自己的决定

`plugin.install` / `uninstall` / `enable` / `disable` 对设备开放。安装一个插件确实等于让
代码跑起来，但一个进程服务一个用户，设备就是这个人本人——这一层真正在管的问题是"装上的
代码能不能替他做某件事"，不是"他能不能装东西"（§3.4）。真正的强制边界在引擎：能力门控、
沙箱、AOT 编译、以及它自己回的那份披露。

`mcp.addServer` 保持拒绝，差别正在这里：它配出来的是一个能起子进程的工具，**没有 manifest、
没有能力声明、没有任何披露**。

### 4.5 一个构建只带一种载体，但包方案不该跟着走

引擎带一种扩展载体，或者一种都不带；脚本载体与 WebAssembly 载体在上游互斥，理由是一个
进程带两个解释器是两倍的攻击面和二十兆。

**互斥的理由只对载体成立，对包方案不成立**——读 manifest、校验、解包、披露不需要任何
运行时，`crates/plugin` 本身也不依赖 wasmtime。但上游把两者绑在同一个 feature 上，所以
今天的脚本构建里 `plugin.*` 一律 `PLUGINS_DISABLED`，**一个包都装不了**。

修法在引擎（拆 feature，并让 manifest 能携带 QuickJS 脚本），见 §9。在 Nest 这边补一套
只会得到两处真相。

在它落地之前，`PLUGINS_DISABLED` **如实透传，不包装成"没有已安装的插件"**：
"这个构建里没有插件子系统"和"一个都没装"是两件不同的事，一个分不清它们的客户端会让人
去找一个永远装不上的包。

### 4.6 包里 Nest 读的那一段

```toml
[[ui]]                          # 界面贡献：同源 ES 模块，浏览器 import
point       = "tool.row"
module      = "rows.js"         # 相对包里的 ui/，只在那底下解析
api_version = 1                 # 贡献点 API，与 [plugin] api_version 是两个数
```

**两个版本号，各由拥有它的一侧检查。** `[plugin] api_version` 是引擎的扩展 API，引擎
校验；`[[ui]] api_version` 是贡献点 API，Nest 校验（§5.1.1）。一个包可以在一边是新的、
在另一边是旧的，所以它们不能是同一个数。

引擎解析 manifest 时忽略它不认识的段，所以这一段不需要引擎配合。Nest 从引擎的插件缓存目录
读同一份 `plugin.toml`，只看它。

`module` **只在 `ui/` 底下解析**——不是约定，是结构上就点不到包里别的文件，所以一个写得
很巧的 `module` 也拿不到脚本、拿不到 manifest。

**披露要合起来。** 引擎装完回的 `disclosure` 是模型可见文本；界面贡献占了哪些点是 Nest
知道的。安装完的那一屏把两半拼起来，否则用户看到的披露是不全的。

**信任级说清楚：界面贡献与页面同级。** 它是同源模块，浏览器没有任何机制能把它关小；CSP 挡
得住外部来源、内联脚本与出网，挡不住一个已经被允许加载进来的同源模块去做页面本来就能做
的事。所以这一层的约束是**披露、准入检查、可吊销与可审计**，不是强制隔离——一个被当成
隔离来依赖的非隔离，比一个已知不隔离的地方危险得多。

真正的强制边界在进程一侧，并且是完整的：引擎侧扩展受能力门控与沙箱约束，命令执行受权限
系统约束，出网受策略约束，RPC 面受授权表约束。一个界面贡献能做的最坏的事，上限是"这个
用户自己能做的事"。

## 5. 界面

### 5.1 界面在二进制里，可以被换掉

**安装物是一个文件。** 界面编译在里面，所以不存在"页面和后端对不上"这种状态——它们是
一起编出来的。

| 形态 | 怎么来 | 用在哪 |
|---|---|---|
| 内嵌（默认） | 编译进二进制 | 单机、边缘节点。装一样东西 |
| `--ui-dir <目录>` | 从磁盘读，整套替换 | 做另一个产品；开发前端时改完刷新 |
| `--headless` | 一张都不发 | 纯 RPC 节点 |
| `nest ui export <目录>` | 把内嵌的那份写出来 | 让 CDN 或代理去发。仍然只有一个安装物 |

**这一节改过一次方向，理由记在这里。** 原来是"后端不含界面，界面是独立产物"，最硬的
论据是插件的界面模块要在运行期 import 进来——而那件事今天由**引擎的插件缓存目录**提供
（§4.6），不需要界面本身是分离的。界面产物 gzip 后 79 KB，编进去二进制从 30.7 涨到
30.9 MB，对着 48 MB 的预算不构成任何取舍。

**可定制这条目标没有让步**：换一整套界面仍然是一个参数，不是一次重编译（§8 第三层）。

#### 5.1.1 版本协商仍然要，使用者变了

界面在握手时声明协议版本、贡献点 API 版本与传输拓扑，后端回自己支持的；不匹配就拒绝
并说清哪一边旧了，**不做静默降级**——一个半兼容的界面产生的 bug 报告是无法处理的。

内嵌之后，**内建界面不可能对不上**，所以协商的使用者只剩两个：

1. `--ui-dir` 换进来的那一套；
2. **包带的界面模块**——这才是常态。

于是包的 `[[ui]]` 要声明它照哪一版贡献点 API 写的，装的时候比对，不匹配就把**那一条**
贡献报成不生效（不是整个包装不上，§2.4）。没声明的照装，但会被说一句——不声明的包多半
早于这个字段，为它们拒绝安装等于一个主要在拒绝正常东西的版本检查。

界面**不假定拓扑**：它拿到的是一个客户端库，库把五种通道语义映射到握手谈定的那种拓扑
上。同一份界面既能走单条双向流，也能放在反向代理后面走分离流。

### 5.2 贡献点

六个，数量本身是设计的一部分。加第七个是一个需要论证的决定，不是一次提交。

**这些是界面自己的接缝。** 它们存在的理由不是给第三方一个扩展面——扩展 agent 是引擎的事
（§4）——而是让界面不是一堆 switch：于是"换一整套界面"是换一批注册，而不是改一堆分支。

| 贡献点 | 贡献什么 | 求值时机 |
|---|---|---|
| `tool.row` | 一次工具调用在流里的那一行 | 该工具块状态变化时 |
| `details.panel` | 详情栏里的一页 | 选中项变化时 |
| `flow.block` | 流里的一种块 | 该块状态变化时 |
| `sidebar.group` | 会话列表的分组与排序 | 会话集合变化时 |
| `command` | 一条斜杠命令及其补全候选 | 命令面板打开时 |
| `settings.section` | 设置面板里的一节 | 设置页打开时 |

完整目录由代码生成，见 `docs/contribution_points.md`。

**外壳必须真的去问。** 一个没人问的贡献点等于只存在于目录里，产品照旧自己直接画，而所有
测试都还是绿的。这件事真的发生过一次，七个点里的五个。判据因此不是"注册了"，是"被问过"，
并且由测试盯着——包括点的名单本身也从生成的目录里读，因为手抄的那份也漂过一次。

一个包可以在这些点上注册（§4.6），走的是同一个注册表、同一份宿主 API。

### 5.3 界面产物的两条硬规矩

- **只用令牌，不写死颜色**——写死颜色的部件在另一种主题下不可读。
- **只用 key，不写死文案**——写死文案让整个界面在切换语言后变成两种语言。

由静态检查强制。CSP 不放宽：`script-src 'self'`、`connect-src 'self'`、无
`unsafe-inline`、无 `unsafe-eval`、无外部源。产物自包含，没有 CDN，没有运行期从网上拉的
依赖——所以断网时界面照常打开。

### 5.4 出网是一项要披露的能力

界面这一侧没有第二条出网通道，CSP 挡住了。这不是顺带的效果，是有意的：出网是一项要在
安装时被看见的能力，不该因为代码跑在浏览器里就绕过披露。要访问外部服务，走引擎侧声明了
`net` 能力的代码，由后端代理。

### 5.5 内建界面走的就是这些点

工具行、流块、详情面板、侧栏分组、命令、设置节——没有一样有私有通道。

**如果连工具行都是这样画出来的，这些接缝就不需要谁来相信。** 反过来说，一个产品自己绕开
的接缝，只存在于目录里，而且绕开的时候一切照常工作——这是最难发现的那种失败。

## 6. 信任与安全

### 6.1 四级

| 级 | 是谁 | 能做什么 |
|---|---|---|
| **内核** | 这个二进制自己 | 全部 |
| **运维本人** | 写在项目/配置目录里的脚本与设置 | 他本来就能亲手做的任何事 |
| **插件** | 装上的包 | 默认什么也够不着；多要一分，安装时写下来一分 |
| **设备** | 远端连上来的客户端 | 授权表上的方法 |

级别按出身定（§2.3）。中间两级由**引擎**判定和强制——同一份 `.js`，放在项目里是运维本人
写的，随插件下载来的就是插件，判据是解析并规范化之后的路径，不是它自称什么。Nest 这一层
只判定最后一级。

### 6.2 强制边界与披露边界

系统里两种边界都有，文档逐处标明是哪一种：

| 强制 | 披露 |
|---|---|
| 引擎侧 WASM 组件的能力门控 | 插件模型可见文本的内容 |
| 命令执行的权限判定与沙箱 | |
| 出网策略（模型选的目标受约束，运维配的端点不受） | |
| RPC 授权表 | |
| 设备配对与吊销 | |

左列除了后两行都是引擎的；Nest 强制的是授权表与设备配对。右列那一条也是引擎产出的，Nest
负责把它摆到人面前（§4.3）。

把这条讲清楚比藏起来有用。**没有第三种边界**——不存在"大概安全"的地方，一个约束要么
被代码强制，要么在装的时候被人看见过。

### 6.3 远程访问

一个进程服务一个用户，但这个用户可能有几台设备。

- **配对**：一次性配对码换一份长期设备凭据（设备侧密钥对，挑战应答）。每台设备一条，
  可列出，可单独吊销。不需要 CA，不需要身份提供方。
- **凭据绑主体，不绑连接。** 多通道拓扑里所有通道共用握手换来的那一份凭据，吊销一台
  设备立即断掉它的全部通道（§3.3.3 第 2 条）。
- **非回环绑定必须同时有 TLS 与已配对设备。** 没有裸 HTTP 的远程——不是默认关闭，是
  没有这条路径。
- 回环绑定同时监听 IPv4 与 IPv6：`localhost` 在多数系统上先解析到 `::1`，只绑一边的
  服务会出现"curl 通了但页面打不开"。
- Origin 校验按部署形态取值：本地放行本地来源，远程只放行配置里写明的来源。界面与后端
  不同源的部署（§5.1 的第二种）必须把界面来源写进配置，**不提供通配**。

### 6.4 敏感数据

transcript、会话记忆、录像（每次模型调用的完整输入，含系统提示词）都是同一批内容，
**敏感级别相同**，落在同一个引擎目录、同一套文件权限下。

三条规则：录像默认开，因为没有它就无法回答"模型到底看见了什么"；录像目录**永不经
HTTP 暴露**，只能通过授权过的方法读取折算后的视图；删除会话连带删除它的录像，关闭
会话不删——会话还能重开。

### 6.5 审计

授权决定、插件调用与其结局、权限回答、设备配对与吊销，写进会话时间线的扩展条目里，
与其余条目同序。

复用引擎的日志机制而不是另建一套，有一个具体好处：**未知命名空间必须可跳过**，所以
卸载一个插件之后，它留下的旧条目仍然能被加载，历史不会因为少了一个插件而读不出来。

## 7. 边缘部署

### 7.1 形态

**一个进程、一个用户、多个会话、一个后端二进制、无运行时依赖。**

没有包管理器，没有运行时，没有 `node_modules`。安装物是这一个文件（加上可选的界面
产物目录）。运行时不从安装目录读任何东西——安装目录只读，状态在数据目录，两者分开，
所以升级就是换掉那个文件。

四种典型部署：

| 形态 | 后端 | 界面 | 传输拓扑 |
|---|---|---|---|
| 单机 | 本机，回环 | 后端提供 | 单双向流 |
| 边缘节点 + 远程使用 | 节点上，TLS + 配对 | 后端提供 | 单双向流 |
| 反向代理后面 | 内网，代理终结 TLS | 独立静态服务 | 分离流 |
| 一堆节点 / 自动化 | 每节点一个进程，`--headless` | 无，或一份共用界面 | 纯请求 |

### 7.2 预算

**一个不被测量的性能目标只是一句话。** 下面这些数进 CI 门禁，回归即失败。初值按
"4 核 8G 小主机，也要能在 2 核 2G 的 arm64 单板上跑"定：

| 指标 | 初值 |
|---|---|
| 后端二进制大小（默认构建） | ≤ 48 MB |
| 界面产物（gzip 后） | ≤ 300 KB |
| 冷启动到可服务 | ≤ 300 ms |
| 空载常驻内存 | ≤ 80 MB |
| 每个空闲会话的内存增量 | ≤ 4 MB |
| 一次 unary 往返 p99（同机） | ≤ 15 ms |
| 每条空闲连接的常驻开销 | ≤ 64 KB |
| 握着 100 条连接时的常驻内存 | ≤ 120 MB |
| 完全空闲时 CPU | < 0.5% |

**「每条空闲连接的常驻开销」测的是预热之后的边际值，这一条要说清楚。** 冷测时头一百条
连接看起来每条 145 KB；开完关掉再开一百条，边际不到 1 KB。差别不在连接上——是分配器
第一次向操作系统要页，然后一直留着。对冷数字设门禁等于对 malloc 设门禁，它的通过与否
和这份代码没多大关系。

所以两个数都测：**再开一条要多少**，以及**握着一百条时一共多少**。后者是操作系统那台
小机器真正要满足的数，也是前者不能被悄悄换掉的原因——单看边际值，一个把内存全在启动时
一次占掉的实现会显得很漂亮。

这些是初值，可以调整——**调整的前提是把新的数写进这张表并说明理由**，不是让门禁静默
放宽。

三个已知的取舍要摆在这里，不藏在实现里：

1. **QuickJS 每次调用建一个全新运行时**，这是"调用之间什么都不留"这条安全承诺的实现
   方式。在高频贡献点上它是成本。是否为某些点复用运行时，是一个会削弱那条承诺的决定，
   要显式做，不能顺手做。
2. **引擎内嵌意味着崩溃不隔离。** 换来的是没有 socket、没有握手、没有子进程管理。补偿
   措施是轮次级的故障隔离（一次崩溃只废掉一个会话）与随发布物提供的进程守护单元，而
   不是把进程拆开。
3. **拓扑的成本不一样，所以它是配置而不是常量。** 分离流在代理后面更好用，代价是多一
   条连接的重连、心跳与常驻开销；单双向流在弱网下更省，代价是所有流量共享一条连接的
   队头。**边缘默认单双向流**，因为那里连接比中间件贵。

### 7.3 离线

边缘常态是网络受限或没有外网。

- 模型走本地端点（OpenAI 兼容协议直连本地推理服务），并按任务分路由：主循环用大模型，
  压缩、子代理、记忆检索用小模型——这几类调用占的次数多、对质量的要求低，是边缘设备上
  最值得省的地方。
- 界面产物自包含，无 CDN（§5.3），所以断网时界面照常打开。
- 插件安装可以完全离线：一个插件是一个目录，从本地路径装与从市场装走同一条披露流程。

### 7.4 故障

- 引擎的持久化是 append-only 的日志，进程消失后重启即恢复到最后落盘的那一轮。
- 被取消的轮次**不写终止标记**——取消是被打断，不是到达终点，所以会话必须保持可续。
- **断线不动 turn。** 任何通道断开只影响观看，中枢照跑；重连后按 `seq` 追赶
  （§3.3.3 第 1 条）。多通道拓扑里一条通道断了不牵连另一条。
- 上游长时间无响应（连接挂住而不是报错）要在界面上表现为可脱出的状态，不是无限"运行中"。

## 8. 改造它的三个层次

| 层次 | 做什么 | 代价 |
|---|---|---|
| **换 profile** | 一份声明式配置：要哪些场景、哪些 provider、哪套界面、哪种传输拓扑 | 不写代码 |
| **装扩展** | 引擎的脚本或插件，改的是 agent 的行为 | 不重编译 |
| **换界面** | 换掉 `--ui-dir` 指的那份产物，或者只换其中几个注册 | 不重编译后端 |
| **换 crate** | 实现内核之上的某个契约 | 重编译后端 |

第三层值得单说：界面是独立产物，六个贡献点是它自己的接缝，所以"做成另一个产品"的下限
不是 fork，是**换一批注册**。这是 §1.2 第一条目标真正落地的地方。

配套的两样，缺一不可：

- **贡献点目录由代码生成**，并有测试盯着它与代码一致。一份会过期的清单比没有更糟——
  它会被当成事实引用。
- **界面的测试不需要浏览器**：一套假 DOM 里跑的是真模块，不是它的副本。跑得起来才有人
  写测试。
- **Agent 行为的测试不需要模型**：引擎的录像按位置重放，所以工具调用、权限提问、子 Agent
  每次都一样，不花钱也不等网络。在有它之前，权限那条路**一次都没被真正跑到过**——配置的
  模型不肯调工具，测试轮轮报"不确定"，而一切看上去是绿的。

扩展 agent 的那一层（脚手架、离线插件测试、载体选择）属于引擎，见 Core 自己的文档。

## 9. 与 AttaCore 的边界

**依赖方式**：以库链接，进程内调用，不起子进程、不走 socket。

**Nest 一侧永远不做的事**：实现或复制任何引擎逻辑；绕过引擎直接操作 transcript；
在引擎之外维护第二份会话状态（中枢维护的是**观看状态**与队列，不是会话本身）。

**需要 Core 提供的**（按对本设计的重要性排）：

1. **包方案与载体解耦**，且 manifest 能携带 QuickJS 脚本。今天两者绑在同一个 feature 上，
   所以出厂构建里一个包都装不了（§4.5）。这一条挡着"用户打包发布插件"这条路的全部。
2. `script_host::engine()`——把载体的引擎交出来，宿主就能把自己的点绑到同一个载体上，用
   引擎的配额、墙钟、来源定级与记账，而不必链接第二个解释器。
3. 引擎装配的一个函数入口，使宿主不必复制装配代码——否则每个宿主都带一份会漂移的复制。
4. `plugin.list` 的条目带上包的根目录，否则宿主要自己拼引擎的磁盘布局。
5. 会话列表条目补齐场景与项目根，否则每个宿主都要自己记一份。
6. 会话重命名、运行中切换模型。**后者没有变通办法**：现在只能改配置层再建会话。
7. 对冷会话的订阅自动恢复，否则每个客户端都要自己实现一段回退。

这些以 issue/PR 的形式提给 Core，**不在 Nest 侧绕过去**。绕过去的代价是两份真相。

## 10. 明确不做的

| 不做 | 理由 |
|---|---|
| 多租户 | 一个进程一个用户。多租户是另一个系统，硬塞进来会让授权模型对单用户场景过度复杂 |
| 可替换的会话中枢 | §2.1 |
| 让拓扑差异渗进中枢或授权 | 传输可以有几种拓扑，但只能有一套语义（§3.3.3 第 5 条） |
| 运行期改变装配 | 等于让别的东西决定这个进程是什么 |
| Nest 侧的第二套插件体系 | 同一件事两处真相，且只有一处真拦得住（§2.2、§4.1） |
| 在 Nest 侧执行包里的任何代码 | 包括没有能力的纯函数。规则不需要例外才守得住（§2.2.1） |
| 给插件贡献的 `nest.*` 方法 | 它需要回调能力，而给出能力就是在 Nest 长出第二个能力模型。没有需求，也不打算有 |
| 界面的运行期外部依赖（CDN、远程 import） | 断网即坏，且把供应链面开到系统之外 |
| 协议层的投影子系统 | 派生视图不属于协议 |
| 把引擎的凭据/子进程/端点类方法开放给设备或插件 | 它们等价于接管这个进程 |

## 11. 路线

**v0 —— 内核成立，界面由自己的接缝拼起来。** ✅
内核四件事、单双向流拓扑、贡献点目录与生成器、每个界面点都由内建注册并且**被外壳真的
问过**、装插件的上传与安装、中英语言包、预算门禁。

判据不是"功能齐了"，是**内建界面没有走任何私有通道**，而且这条由测试盯着——它失守过
一次，七个点里的五个，当时所有测试都是绿的。

**v1 —— 能被别人装上。**
分离流拓扑、设备配对与远程、审计条目。

分离流排在配对前面是有意的：它是"语义写死、拓扑可选"这条结构赌注的**证伪实验**，而判据
可以机检——`git diff crates/hub crates/authz` 必须为空。不为空就说明语义被拓扑污染了。
把配对、凭据、TLS 压上去之后再发现这件事，返工面要大得多。

**v2 —— 能被别人改造。**
界面整体替换的文档与样例、纯请求拓扑、跨会话搜索与导出。

每一阶段的验收都包含一条：**照文档从零换一套界面，不问作者**。

## 12. 与业界的位置

这一节的作用是说明哪些决定是共识、哪些是这套设计的选择。

近两年出现的几个 agent 宿主（DeepSeek Harness / dsh、以及围绕 MCP 生态生长出来的
若干 IDE 与桌面宿主）在几件事上给出了同样的答案，Nest 也照做：**一切能力以插件形式
接入**、**模型是可换的类别而不是硬编码**、**会话是可追加、可回放的事件流**、
**界面与内核分离**、**请求与事件流分开承载**。这些不是差异点，是这类系统的形状。

有一处形状不同：那类宿主自己长着一套插件系统。Nest 没有，因为它下面已经有一个——扩展模型
整件事在引擎里，宿主只补引擎有意不做的那一步（§4）。

传输拓扑上尤其没什么可争的：那类系统普遍采用"一条 unary 端点 + 若干只下行事件流 +
一条带外应答端点"的分法，理由与 §3.3 列的一致。Nest 的做法是把这套分法**上升成语义、
把连接数下降成配置**——因为同一套语义在边缘设备上更适合收敛成一条连接，而在代理后面
更适合摊开成几条，这两种部署都在目标之内。

分歧在四处：

**一、内核边界。** 那类系统多把"一切皆插件"推到底——agent 循环、会话持久化、审批
逻辑本身也是可换插件。代价是这个系统不再保证任何东西：当循环本身可换时，"一轮是
什么"没有答案。Nest 反过来，骨架写死、判断开放（§2.1）。这牺牲了一部分灵活性，换来
的是可以对用户做出承诺。

**二、插件的运行方式与隔离。** 以 Node 为宿主的方案里，插件与内核同进程同权限，
JS 的对象级隔离不是隔离；其沙箱通常只覆盖文件系统的几档模式，不含网络与进程隔离。
这套设计里插件跑在引擎侧，两档载体（QuickJS 的无 I/O 运行时、WASM 的能力门控）都是真
约束，而宿主这一侧根本没有插件在跑——**没有需要被相信的隔离，是因为没有那个位置**。
差别不在"更安全"这个形容词上，在于每一处都标明了自己是哪一种。

**三、模型可见文本的处理。** 这一类攻击面在多数方案里没有专门位置：沙箱管执行，
而一段进入系统提示词的文字既不越权也不出网。引擎把它当作一等的披露对象，从安装里回出来；
宿主的活是把它摆到人面前，而不是自己再算一遍（§4.3）。

**四、部署形态。** 以 Node 或容器为前提的宿主，安装物是一棵依赖树，冷启动以秒计，
常驻内存以百兆计。Nest 的后端是一个二进制，预算写进 CI（§7.2）。这条不是性能偏好，
它决定了这个系统能不能装在一台边缘设备上——而"能装在边缘设备上"是 §1.2 的目标之一。

值得从那些系统里继续借的，是它们对**分层配置**的处理（插件 → 打包 → profile →
覆盖层，让"换一个形态"变成一次配置而不是一次 fork）。Nest 的 profile（§8）就是这条
思路的最小版本。
